# 单写者运行与验收说明（J11 / P4）

**适用版本：** J11 集成基线（`j11/expr-consolidation`）
**相关代码：** `apps/desktop/sidecar/locking.py`、`apps/desktop/sidecar/pcs_bridge.py`（`DATA_LOCKED`）

---

## 1. 这条约束是什么

一个桌面应用实例，最多只能有一个 sidecar 写同一个 PCS 数据实例。

- 锁绑定**一个数据库路径**，由操作系统文件句柄持有；
- 进程异常退出时**由操作系统释放**（不会留下永久死锁）；
- **锁文件本身从不删除**，所以一个残留文件不会挡住下一次启动；
- 锁在打开任何 SQLite 连接**之前**取得 → 第二个 sidecar 不会对同一库建立写连接，而是直接返回 `DATA_LOCKED`。

**这不是"PCS 全局互斥"**：不同数据实例（不同库路径）可以同时运行。

## 2. 怎么判断自己撞上了

| 观察点 | 表现 |
|---|---|
| 桥接错误码 | `DATA_LOCKED` |
| `app.info` | `data_locked=true`、`ready=false` |
| 宿主日志 | 启动期一行 `data_locked=%s ready=%s session_id=%s` |
| 界面 | 聊天不可用；不产生新 turn、不写库 |

**判据：** 只要 `data_locked=true`，本轮任何写操作都不应被解释为"产品故障"——它是设计中的拒绝。

## 3. 怎么恢复

按顺序尝试：

1. **关闭其它 QUINTESSENCE 桌面实例**（包括残留的托盘进程）。最常见原因就是开了两个。
2. **确认没有第二个 sidecar 进程**：
   - Windows：任务管理器里查 `quintessence-desktop.exe` 与 sidecar 子进程；
   - 只应剩下你要用的那一个。
3. 仍被锁 → **关闭全部实例后重开**。文件句柄随进程消失，锁文件残留不影响启动。
4. 仍失败 → 记录：库路径、`app.info`、宿主日志尾 50 行，再排查（**不要手工删锁文件当作修复**，它按设计无害，删它只会掩盖真实原因）。

## 4. 验收时怎么操作

单写者必须被**主动验证**，不能只看"能启动"：

1. 启动实例 A，确认 `app.info` → `data_locked=false`、`ready=true`。
2. 在同一数据路径**再启动一个 sidecar**（第二实例）。
3. 断言：第二个返回 `DATA_LOCKED`，`data_locked=true`，且**没有**新 turn / 新写入产生。
4. 关闭 A，重开 A → 恢复 `ready=true`（证明锁随进程释放）。
5. 用不同数据路径再启一个实例 → 允许同时运行（证明锁是"按库"而非全局）。

**证据要求：** 两次 `app.info` 输出、第二条的错误码、关闭重启后的 `app.info`。

## 5. 已知限制

- 锁的粒度是**数据库路径**，不是"用户"或"设备"。
- 网络盘/符号链接路径若解析到不同真实路径，可能绕过同一性判断（未验证）。
- 本说明不改变任何代码行为；它只是把既有契约写成可执行步骤。
